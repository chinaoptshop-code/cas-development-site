# Адмінка сайту: як редагувати сайт і вести замовлення самому

Адреса: **https://cas-develop.com/kabinet/admin**

Тут можна без програміста й без Claude:

- вести **CRM** — замовлення Оздоби й заявки з сайту, статуси, відповідальних, нотатки, суми, дати дзвінків;
- редагувати **товари Оздоби**, **статті блогу**, **сторінки послуг (лендинги)**, **меню й футер**, **тексти звичайних сторінок**;
- завантажувати **фото**;
- дивитися **історію змін** і **відкочувати** невдалі правки;
- вести **проєкти клієнтів**: етапи, фотозвіти, документи (клієнт бачить їх у своєму кабінеті).

---

## 1. Як зайти

1. Відкрийте https://cas-develop.com/kabinet/admin.
2. Увійдіть через **Telegram**, **Google** або **номер телефону** (так само, як клієнти).
3. Після входу кожен потрапляє у **свій** інтерфейс: власник — у майстер-панель `/kabinet/admin`, працівники —
   у кабінет працівника `/kabinet/team`, клієнти — у `/kabinet`. Чужий інтерфейс — сторінка «Немає доступу» (403).
   Працівників додає власник у вкладці **Персонал** — див. розділ 12 «Персонал і ролі». Старий спосіб (секрети
   `SHOP_ADMIN_TG_IDS` / `SHOP_ADMIN_EMAILS`) теж працює: такі люди автоматично стають **менеджерами**.

Кожен запит адмінки сервер перевіряє окремо: без входу адміністратора нічого не читається й не змінюється.

## 3. Як працює збереження

1. Натискаєте **Зберегти** → сервер записує зміну в GitHub одним «комітом» (як фото «до/після» у історії).
2. GitHub сам перезбирає сторінки з цих даних і викладає сайт на Cloudflare. Це **2–4 хвилини**.
3. У вкладці **Історія** видно статус збірки: «ок» — зміни вже на сайті; «йде…» — зачекайте; «помилка» — див. розділ 5.

Якщо хтось (ви в іншій вкладці, Claude чи інший менеджер) змінив той самий файл раніше — адмінка не перезапише його,
а скаже «Файл уже змінено». Оновіть сторінку й повторіть.

Адмінка може змінювати лише контент: товари, статті, лендинги, меню, тексти сторінок, фото. Код сайту, налаштування
й бази даних вона змінити не може — це захист від випадкових поломок.

## 4. Токен GitHub (потрібен для редагування сайту)

Без токена працюють CRM, замовлення, клієнти, проєкти й коди партнерів, а вкладки редагування пишуть «Потрібен токен».

Створити токен (одноразово, ~5 хвилин):

1. Увійдіть на https://github.com під акаунтом, якому належить репозиторій `chinaoptshop-code/cas-development-site`.
2. Відкрийте https://github.com/settings/personal-access-tokens/new (Settings → Developer settings →
   Personal access tokens → **Fine-grained tokens** → **Generate new token**).
3. Заповніть:
   - **Token name**: `cas-admin`
   - **Expiration**: 1 рік (або «No expiration»). Запишіть у календар дату, коли треба буде створити новий.
   - **Repository access**: **Only select repositories** → виберіть лише `cas-development-site`.
   - **Permissions → Repository permissions**:
     - **Contents** — **Read and write** (обовʼязково);
     - **Actions** — **Read-only** (необовʼязково: щоб в «Історії» було видно статус збірки);
     - **Metadata** — Read-only (ставиться сам).
4. **Generate token** → скопіюйте рядок, що починається з `github_pat_…` (його показують один раз).
5. Відкрийте репозиторій → **Settings → Secrets and variables → Actions → New repository secret**:
   - **Name**: `SHOP_GITHUB_CONTENT_TOKEN`
   - **Secret**: вставте токен → **Add secret**.
6. Запустіть деплой, щоб сайт отримав токен: вкладка **Actions** → «🚀 Deploy to Cloudflare Pages» → **Run workflow**.
7. Через 2–3 хвилини оновіть /kabinet/admin — вкладки редагування запрацюють.

Токен нікуди більше не вставляйте й нікому не пересилайте. Якщо він «засвітився» — видаліть його на тій самій сторінці
GitHub і створіть новий (кроки 2–6).

## 5. Якщо збірка впала (в «Історії» — «помилка»)

На сайті в цей час лишається **попередня робоча версія** — нічого не ламається для відвідувачів.

1. В «Історії» знайдіть свою останню зміну й натисніть **Відкотити**. Через 2–4 хвилини збірка пройде знову.
2. Подивитися причину: натисніть на червону позначку «помилка» → відкриється сторінка GitHub Actions → крок з ❌ →
   останні рядки. Найчастіше:
   - `❌ tools/blog/articles/…: …` — у статті бракує поля, фото не знайдено, опис довший за 160 символів,
     два фото поспіль чи фото на початку тексту. Виправте статтю й збережіть знову;
   - `немає фото … для товару …` — фото товару не завантажилось; видаліть і додайте фото ще раз;
   - помилка JSON у лендингу — у вкладці «Лендинги» відкрийте сторінку, перемкніться на «JSON» і виправте.
3. Якщо незрозуміло — надішліть посилання на сторінку помилки Claude чи розробнику.

## 6. Як відкотити будь-яку зміну

Вкладка **Історія** → рядок зі зміною → **Відкотити**. Створиться новий запис, що повертає файли до стану «до».
Нічого не губиться: відкат теж можна відкотити.

Якщо адмінка пише «Ці файли змінювали пізніше» — спершу відкотіть новіші зміни тих самих файлів (вони вище в списку).
Автоматичні записи «[rebuild]» (перезбірка сторінок) не відкочуються — відкочуйте зміну, яка їх викликала.

## 7. CRM і Google-таблиця

- Замовлення з кошика Оздоби потрапляють у CRM автоматично.
- Заявки з форм сайту потрапляють у CRM автоматично: форма надсилає їх одночасно на сайт (`/api/leads`) і в n8n
  (старий ланцюжок «Contact Form → Telegram» працює як раніше). Якщо n8n теж пересилає заявку на `/api/leads` —
  дубля не буде: та сама заявка з того самого номера за 10 хв записується один раз.
- Google-таблиця **«CAS — CRM замовлень»** (папка з іншими таблицями CAS CRM у Google Drive): аркуші «Замовлення»,
  «Клієнти», «Товари», «Постачальники», «Як працює». У n8n є workflow
  «CAS — заявки й замовлення сайту → Google Sheets (CRM)»: він додає рядок у «Замовлення». Щоб він працював
  на кожну заявку, у workflow «Contact Form → Telegram» додайте наприкінці вузол **HTTP Request** (POST
  `https://n8n.china-opt-shop.pp.ua/webhook/cas-crm-sheet`, тіло — той самий JSON) або **Execute Workflow**,
  і активуйте новий workflow (перемикач Active).
- **Сторінка-джерело** (з 16.11.2026): з якої сторінки сайту людина перейшла на сторінку з формою (кейс, 3D-тур, стаття →
  лендинг або контакти). У списку CRM — позначка «← /proekty/…» біля джерела (клік — показати всі заявки з цієї сторінки),
  у картці — рядок «Сторінка-джерело» з посиланням, у фільтрах — поле «Сторінка-джерело» (точний шлях; зі «/» у кінці,
  напр. `/proekty/`, — усі сторінки розділу), в «Аналітиці» — таблиця «По сторінках-джерелах», у CSV — колонка
  «Сторінка-джерело». Бачать власник і менеджер (право «Усі заявки»); працівникам з призначеними заявками вона не показується.
  Рядок «Перед цим: /шлях» у коментарі лишається (його бачать n8n, Telegram і старі заявки, де окремого поля ще немає).

  **Для розробника:** `assets/lead-form.v1.js` шле `ref_path` (шлях `document.referrer`, лише той самий сайт і інша сторінка);
  `functions/api/leads.js` (`refPath`) приймає лише `/шлях` без домену, `//`, query/hash, пробілів і `< > " ' \`, ≤ 160 символів,
  інакше — `null`; колонка `orders.ref_path` — міграція `migrations/0011_lead_ref.sql` (деплой застосовує міграції сам:
  `wrangler d1 migrations apply` у `.github/workflows/deploy.yml`; до міграції заявка зберігається без поля). `crm.js`: `?ref=`,
  `by_ref` у `?stats=1`, CSV; поле вирізається без `leads.view_all`. Тести — `node tools/tests/run.mjs`, `node tools/tests/ui.mjs`.
- **Зовнішнє джерело** (з 22.11.2026): з якого сайту людина прийшла на cas-develop.com (Google, ChatGPT, Perplexity, Instagram, Telegram…),
  навіть без UTM — у списку позначка «↗ Google», у картці рядок «Зовнішнє джерело: Google (google.com.ua)», у фільтрах — «Звідки прийшли»,
  в «Аналітиці» — «По зовнішніх джерелах», у CSV — колонка «Зовнішнє джерело», у Telegram — «Джерело: …»; бачать ті самі ролі, що й сторінку-джерело.
  Браузер запамʼятовує лише хост (без шляху й параметрів) у sessionStorage на першому заході в сесії й шле його з заявкою (`ref_host`);
  сервер (`functions/_refhost.js`) приймає лише валідне імʼя хоста, колонка `orders.ref_host` — міграція `0019_lead_ref_host.sql` (застосовує деплой).

## 8. Сповіщення про заявки (Telegram, 15 хвилин)

**Що відбувається саме:**

1. Хтось залишає номер на сайті або оформлює замовлення в Оздобі → за кілька секунд **кожному адміну** (Telegram-ID із
   `SHOP_ADMIN_TG_IDS`) бот сайту пише: послуга, сторінка, телефон (натисніть на номер — Telegram запропонує подзвонити),
   імʼя, коментар, UTM, час. Під повідомленням дві кнопки:
   - **✅ Взяв у роботу** — заявка стає «В роботі», відповідальний — той, хто натиснув, рахується **час реакції**
     (хвилини від заявки до натискання). У всіх адмінів повідомлення змінюється на «✅ Взяв <імʼя> за N хв».
     Хтось уже взяв — бот так і скаже;
   - **📋 Відкрити в CRM** — адмінка на вкладці CRM.
   Перетягнути картку з «Нове» в будь-яку іншу колонку CRM або натиснути на картці **Взяти в роботу** (з 18.11.2026; на телефоні
   в нової заявки замість вибору стадії — лише ця кнопка) — те саме, що натиснути «Взяв у роботу» в Telegram: стадія «В роботі»,
   відповідальний — ви, рахується час реакції.
2. Якщо за **15 хвилин** ніхто не взяв — нагадування «⏰ Заявка без відповіді 15 хв…», ще за **60 хвилин** — друге
   (і все, далі — у вечірньому звіті). **Уночі (22:00–08:00 за Києвом) нагадувань немає** — вони приходять о 08:00.
   Сама заявка приходить завжди, і вночі теж.
3. О **20:45** — звіт за день: скільки заявок і замовлень, скільки взято, середній і максимальний час реакції, скільки
   вклалися в 15 хв і які заявки лишилися без відповіді.
4. Час реакції видно в CRM: на картці (⏱, червоним — якщо більше 15 хв), у таблиці (колонка «Реакція»), у картці
   заявки й у CSV.

**Що треба зробити Михайлу:**

- **Кожен адмін один раз відкриває бота сайту в Telegram і натискає «Start»** (без цього Telegram не дозволяє ботові
  писати першим). Бот відповість «Готово: сюди приходитимуть нові заявки…».
- Секрети `SHOP_TELEGRAM_BOT_TOKEN` і `SHOP_ADMIN_TG_IDS` уже є — для миттєвих сповіщень більше нічого не потрібно.
- Для нагадувань, звіту й кнопки «Взяв у роботу» потрібен секрет **`SHOP_LEAD_INGEST_KEY`**. Якщо його ще немає:
  1. Придумайте довгий випадковий рядок (30+ латинських літер і цифр, наприклад з менеджера паролів).
  2. GitHub → репозиторій → **Settings → Secrets and variables → Actions → New repository secret**:
     Name `SHOP_LEAD_INGEST_KEY`, Secret — цей рядок → **Add secret**.
  3. **Actions** → «🚀 Deploy to Cloudflare Pages» → **Run workflow** (сайт отримає ключ).
  4. Готово: **Actions** → «⏰ Заявки — SLA 15 хв і звіт» запускається сам кожні 5 хвилин (GitHub іноді запізнюється на
     кілька хвилин — це нормально). Перший запуск сам підключить кнопки бота (вебхук).
- Кнопка «Взяв у роботу» нічого не робить? Отже, оновлення бота забирає інша програма (наприклад, n8n з Telegram Trigger
  для цього ж бота). Тоді: **Actions** → «⏰ Заявки — SLA 15 хв і звіт» → **Run workflow** → `webhook` — бот перейде на
  сайт (вхід на сайт за номером телефону бот сайту теж обробляє сам). Звіт за сьогодні вручну — те саме з `report`.

**Для розробника:** `functions/_alerts.js` (тексти, кнопки, SLA, звіт, вебхук), `functions/api/tg/webhook.js`
(кнопка «Взяв у роботу» лише від `ADMIN_TG_IDS`; вхід за номером за протоколом `tools/shop/PHONE_LOGIN.md`; Telegram
підписує запити заголовком `X-Telegram-Bot-Api-Secret-Token`, виведеним з токена бота), `functions/api/admin/lead-sla.js`
(ключ `x-lead-key`), `.github/workflows/lead-sla.yml`, міграція `migrations/0006_lead_alerts.sql` (`taken_at`,
`reaction_min`, `reminders`, `tg_alerts`). Нагадування й звіт — лише для заявок, про які бот сповіщав (не для внесених
вручну й не для старих). Локальна перевірка: `wrangler pages dev` з `.dev.vars` (`TELEGRAM_API_BASE` — адреса мок-сервера
Bot API, `ALERTS_TEST_CLOCK=1` — дозволяє підміняти час полем `now` у `lead-sla`); у продакшні ці дві змінні не задаються.

## 8а. Партнери і бот пошуку (з 17.11.2026; з 18.11.2026 — розділ «Контакти», див. розділ 15)

Бот пошуку заявок (працює на Mac mini, Telegram-помічник) читає групи й сайти, знаходить людей, яким потрібні ремонт,
дизайн чи будівництво, і показує їх Михайлу з кнопками **«В CRM»** і **«Не цікаво»**. Тих, хто пише не як клієнт, а як
підрядник, бригада, постачальник, ріелтор, будівельна компанія чи дизайнер, бот не викидає, а зберігає в базу **«Партнери»**
для майбутньої співпраці.

**Розділ «Партнери»** у `/kabinet/admin` (бачать власник і менеджер; дизайнер, прораби, бухгалтер — ні):

- список із фільтрами: тип (бригада/підрядник, постачальник, ріелтор, будівельна компанія, дизайнер/архітектор, інше),
  статус (**новий / цікавий / співпрацюємо / не цікавий**), місто чи область, пошук (імʼя, компанія, @username, телефон, тег, нотатки);
- картка: імʼя, компанія, тип, місто, публічні контакти (Telegram @username, телефон, сайт), теги, нотатки, статус,
  «Вперше / востаннє / разів» і список «Де бачили» (група або сайт + посилання на повідомлення);
- **«+ Партнер»** — додати вручну; **CSV** — вивантаження списку з поточними фільтрами (для Excel / Google Таблиць);
- кожна зміна й експорт — у журналі аудиту («Новий партнер (база)», «Зміна партнера (база)», «Експорт партнерів»).

Один і той самий партнер не дублюється: якщо збігається Telegram, телефон (у будь-якому форматі), сайт (з `www` чи без)
або назва компанії (без «ТОВ», «ФОП», лапок) — бот лише оновлює запис: «Разів» +1, дата «востаннє», нове джерело й теги.
**Статус і нотатки веде менеджер — бот їх ніколи не змінює.** Зберігаються лише публічні контакти з оголошень.

**Заявки з бота** («В CRM») потрапляють у звичайну CRM з джерелом **«Бот пошуку»** (фільтр «Джерело → Бот пошуку»):
послуга, місто, площа, бюджет, оцінка бота, скор, посилання на повідомлення, уривок тексту, Telegram автора. Та сама
заявка вдруге не створюється. Сповіщення в Telegram («Взяв у роботу», SLA 15 хв) — лише якщо бот попросив (`notify: true`).

### Ключ бота `LEADBOT_KEY` — як налаштувати (один раз)

1. Згенеруйте довгий випадковий ключ (≥ 32 символи), наприклад на Mac: `openssl rand -hex 32`. Нікуди його не пишіть
   у репозиторій, чати чи нотатки — лише у два місця нижче.
2. **Сайт.** GitHub → репозиторій → **Settings → Secrets and variables → Actions → New repository secret**:
   Name **`SHOP_LEADBOT_KEY`**, Secret — ключ → **Add secret**. Потім **Actions → «🚀 Deploy to Cloudflare Pages» → Run workflow**:
   деплой сам кладе його в секрети Cloudflare Pages як `LEADBOT_KEY` (як інші ключі сайту).
   Інший шлях — Cloudflare → **Workers & Pages → cas-development-site → Settings → Variables and Secrets → Add →
   Type: Secret**, Name `LEADBOT_KEY` (Production) → Save → перевикласти сайт. Якщо задано обидва, при деплої переможе GitHub-секрет.
3. **Бот (Mac mini).** Ключ — у змінній середовища `LEADBOT_KEY` процесу бота: файл `.env` бота поза репозиторієм
   (права `chmod 600`) або Keychain / launchd-plist, адреса API — `https://cas-develop.com`. Бот шле його в заголовку
   `X-Bot-Key` з кожним запитом.
4. Перевірка: `curl -s -H "X-Bot-Key: $LEADBOT_KEY" "https://cas-develop.com/api/bot/feedback?limit=1"` → `{"items":[…]}`.
   `401` — ключ не той; `503` — сайт ще не отримав ключ (крок 2) або ключ коротший за 24 символи.
5. Зміна ключа (витік, новий Mac): новий ключ у кроках 2–3; старий перестає працювати після деплою.

Захист: без ключа або з невірним — `401`; після 20 невдалих спроб з однієї адреси за годину — `429` (навіть з вірним ключем
до кінця години); з вірним ключем — до 1200 запитів на годину. Ключ порівнюється рівночасово (за часом відповіді не вгадати).
Будь-яке поле з HTML (`<тег>`, `&lt;`…) → `400`; довгі тексти обрізаються; телефони, @username і посилання перевіряються.

## 10. Безпека (аудит 25.10.2026)

- **Усі `/api/*`** проходять `functions/api/_middleware.js`: зміни (POST/PATCH/DELETE) — лише з нашого Origin
  (cas-develop.com / той самий хост), не `Sec-Fetch-Site: cross-site`, тіло — лише `application/json` (інакше 403/415);
  тіло до 64 КБ (редактор — до 31 МБ); відповіді з `nosniff`, `X-Frame-Options: DENY`, CSP `default-src 'none'`, без CORS.
- **Сесія** `cas_s`: HttpOnly, Secure, SameSite=Lax, підпис HMAC; клієнт — 30 днів, **адмін — 7 днів** (старіші адмінські
  cookie не приймаються — увійти заново). Секрет підпису — `SHOP_SESSION_SECRET` (необовʼязково; його зміна = вихід усіх).
- **Ліміти** (`functions/_rate.js`, таблиця `rate_hits`, міграція 0007; IPv6 — за /64): заявки 5/год з IP, замовлення 10/год,
  перевірка коду партнера 20/год (і окремо 20/год замовлень з кодом), вхід Telegram/Google 30/год, вхід за номером 5/год.
- **Ліміти записів працівників** (з 19.11.2026, `STAFF_LIMITS` у `functions/_rate.js`) — на годину **на акаунт працівника**, а не на IP
  (в офісі всі за однією адресою): картки й канбан CRM 600, журнал «КП надіслано» 120, масові дії 60, контакти 600, замовлення Оздоби 600,
  коди партнерів 120, персонал 120, збереження сайту 300; обʼєкти — як раніше 600 з IP. Далі — «Забагато змін поспіль» (429). Розділ 17.
- **Антиспам форми** без капчі: приховане поле `hp` і `t_ms` (заявка швидше 1,5 с після відкриття сторінки — бот);
  бот бачить «успіх», заявка не зберігається.
- **Заголовки сторінок** — `_headers` (CSP з переліком реальних джерел; для `/kabinet*` — ще `'unsafe-eval'` для віджета
  Telegram; для `/kabinet/admin*` — `frame-ancestors 'none'`, `no-referrer`). Нове зовнішнє джерело (скрипт, iframe,
  API) — спершу додати в CSP у `_headers`, інакше браузер його заблокує.
- CSV-експорт CRM екранує формули (`=`, `+`, `-`, `@`); клієнт у `/api/orders` бачить лише свої поля (без `crm_note`).

**Аудит після CRM v2 (19.11.2026).**
- **Працівника, адміна й власника впізнаємо лише за підтвердженим контактом**: Telegram id; пошта — тільки з входу через Google;
  телефон — тільки підтверджений ботом (акаунт входу за номером або `clients.phone_verified`, міграція 0017 — її ставить
  `functions/api/auth/phone/confirm.js`). Телефон чи пошта, які людина вписала в профіль, замовлення або які потрапили з заявки
  (`clients.phone`, `clients.email`), ролей не дають — `verifiedEmail` / `verifiedPhone` у `functions/_lib.js`. Нову перевірку
  «хто це» писати лише через них і `tgOf`.
- **Журнал етапу веде сервер**: історію (`hist`), позначку «погодив сам клієнт» (`approved_by`), останні правки клієнта
  (`rev_note`, `rev_at`) і відлік нагадувань (`review_at`, `remind_at`, `remind_n`) «Зберегти проєкт» бере зі збереженого етапу,
  а не з форми; канал «надіслав бот» вручну в журнал не записати.
- **Довідники «ключ → підпис»** (статуси, канали, типи) — `dict()` з `functions/_lib.js` (без прототипу): значення з запиту на
  кшталт `constructor` не проходять перевірку. Нову мапу, в якій шукають за рядком із запиту, оголошувати через `dict()`.
- Без права `clients.contacts` (бухгалтер) у відповідях немає й адреси доставки та адреси з профілю клієнта.
- Невірний ключ `x-lead-key` — до 20 спроб на годину з адреси (далі 429), як і ключ бота.
- Бот при вході за номером попереджає: ділитися номером лише якщо вхід почали самі (посилання може надіслати стороння людина).
- `_headers`: правило CSP для 3D-турів потрібне кожній мові (`/<мова>/tury/*`) — бракувало для `pt`.
- Тести: `node tools/tests/sec.mjs` (входить у `run.mjs`) і `node tools/tests/xss.mjs` (Playwright: у всі текстові поля — рядки з
  тегами й лапками, далі обхід трьох інтерфейсів; жоден рядок не має стати розміткою).

**CRM v4 (20.11.2026): задачі й таблиці контактів.**
- **Задачі — лише в межах прав**: без `tasks.manage` працівник бачить і змінює тільки задачі, призначені йому (жоден фільтр чи пошук
  цього не розширює; чужа задача — 404). Привʼязаний обʼєкт, заявку чи контакт сервер віддає лише якщо їх і так видно цьому
  працівнику (`shapeTasks` у `functions/_tasks.js`: `projectScope`, `orderScope`, `contacts.linked`, телефони — з `clients.contacts`).
- **Тексти задач** (назва, примітка, коментар виконавця) сервер приймає як є — будь-які символи; екранує інтерфейс і тексти для
  Telegram (`escHtml`). Нове місце показу — лише через `esc()` (перевіряє `xss.mjs`).
- **Таблиця контактів**: сортування — тільки за колонками зі списку `SORT` (у SQL потрапляє вираз зі списку, не текст запиту);
  імпорт, масові дії, архів — право `partners.base`; без `clients.contacts` телефон, Telegram і пошта не віддаються ні в таблиці,
  ні в картці, ні в CSV. Тип і статус з імпорту шукаються в довідниках без прототипу (`dict()`).
- **Ліміти**: задачі — 600 записів на годину на працівника, масові дії — 60, порції імпорту — 120 (до 100 рядків у порції).
- Підміна годинника `x-test-now` діє лише з `ALERTS_TEST_CLOCK=1` (локальні тести); у продакшні змінної немає.

## 11. Онлайн-контроль обʼєкта (кабінет клієнта /kabinet/obiekt)

Клієнт бачить свій обʼєкт: етапи зі статусами й прогресом, стрічку фотозвітів, акти етапів і документи, графік платежів

Усе вносить менеджер в адмінці: вкладка **Обʼєкти** → відкрийте проєкт (або **+ Новий проєкт**, розділ 13).

**Етапи.** У блоці «Етапи: статус і прогрес» — назва, статус (заплановано / в роботі / приймання / виконано / пауза),
повзунок відсотка, дати, примітка; **+ етап** — новий. Натисніть **Зберегти проєкт** — тоді етап отримає внутрішній id,
і до нього можна привʼязати фотозвіт, акт чи платіж (у списках «Етап» нові етапи зʼявляються після збереження).

**Фотозвіт (раз на 1–2 тижні).** Під «Фотозвіти»: дата, заголовок («Тиждень 5: стяжка»), **Етап**, опис. Фото:
- кнопка **Завантажити фото** (потрібен токен GitHub, розділ 4) — фото стискаються у WebP, кладуться в `img/uploads`,
  посилання підставляються самі; на сайті фото зʼявляться за 2–4 хв після збірки;
- або вставте https-посилання, по одному в рядку (Google Drive з доступом «за посиланням», власне хмарне сховище).
Потім **Додати фотозвіт**. Клієнт бачить звіт у стрічці; кнопка біля етапу фільтрує звіти цього етапу.

**Акт етапу.** У «Документи»: тип **Акт етапу**, етап, назва («Акт етапу 2»), посилання на PDF → **Додати документ**.

**Графік платежів.** Схема в кожного клієнта своя: заповніть рядок (назва, етап, %, сума й валюта, дата за планом,
статус, примітка) → **Додати платіж**, або натисніть заготовку **50/50**, **50/30/20**, **50/40/10** — додадуться рядки з %,
далі вкажіть суми й дати. Статус і дату можна міняти прямо в таблиці; «Оплачено» ставить фактичну дату сам.

**Камера 24/7 (за доп. оплату; ціну на сайті не вказуємо — «за запитом»).** Поле **Камера 24/7 — посилання** у формі проєкту
→ **Зберегти проєкт**. Що вставляти:
- **YouTube-трансляція** з доступом «за посиланням» (`https://youtube.com/live/…` або `https://youtu.be/…`) — відтворюється
  прямо в кабінеті (через youtube-nocookie.com; вмикається лише після натискання клієнтом);
- **пряме посилання на кадр** `.jpg/.png/.webp` (деякі камери/NVR дають «snapshot URL») — кадр з кнопкою «Оновити кадр»;

## 13. Обʼєкти: проєктування й ремонт в одній CRM (з 17.11.2026)

**Новий проєкт** — вкладка **Обʼєкти** → **+ Новий проєкт**: тип (Дизайн-проєкт / Ремонт / Будівництво / Комплектація меблями /
Ландшафт / Інше), назва, клієнт, адреса, площа, сума договору й валюта, **дата здачі**, відповідальний і (за бажанням) **графік
платежів** 50/50, 50/30/20 або 50/40/10. Етапи підставляються з шаблону типу (видно у формі ще до створення):
- Дизайн-проєкт: Бриф → Замір / 3D-замір → Планувальне рішення → Концепція / колажі → 3D-візуалізації → Робочі креслення → Специфікації й комплектація → Авторський нагляд;
- Архітектурний проєкт (з 18.11.2026): Ескізний проєкт → АР — архітектурні рішення → КР — конструктивні рішення → ОВ / ВК / ЕО (за завданням) → Генплан → Супровід дозвільних документів;
- Ремонт: Демонтаж → Чорнові роботи → Інженерні мережі → Штукатурка й стяжка → Чистове оздоблення → Меблі й техніка → Здача й прибирання;
- Будівництво: Проєкт і дозволи → Фундамент → Коробка → Покрівля → Вікна й фасад → Інженерія → Оздоблення → Благоустрій → Здача;
- Комплектація меблями: Підбір і специфікація → Погодження → Замовлення → Виробництво → Доставка → Монтаж;
- Ландшафт: Обміри й зйомка → Концепція → Робочий проєкт → Земляні роботи й дренаж → Мощення → Озеленення → Здача; Інше — без етапів.
Платежі схеми привʼязуються до етапів: аванс — до першого, проміжний — до середнього, останній — до останнього; суми рахуються від
суми договору. Етапи й платежі потім змінюються в картці проєкту, як раніше.

**Список проєктів:** вкладки **Усі / Проєктування / Ремонт і будівництво**, фільтри (тип, стан, відповідальний, «Лише прострочені»),
пошук за назвою, клієнтом, телефоном чи адресою. Колонки: тип, поточний етап із прогресом, **Здача** (червоне «прострочено», якщо дата
минула, а проєкт не завершено), **Задачі X/Y**. Прострочені платежі (не оплачені після дати за планом) — червона позначка в списку й
у графіку платежів.

**Задачі по етапах (чекліст).** (З 20.11.2026 ці задачі видно й у вкладці «Задачі» поруч із загальними — розділ 18; під чеклістом у
картці обʼєкта — блок «Задачі» з іншими задачами цього обʼєкта.) У картці проєкту, під етапами: задача, етап, виконавець, термін → **Додати задачу**. Виконавцю
приходить Telegram, і він бачить задачу в `/kabinet/team` → «Сьогодні» (прострочена — червона) та в картці обʼєкта, де відмічає
**Виконано**. Якщо виконавця ще не було в команді обʼєкта — його додано автоматично. Прораб/дизайнер можуть додати задачу лише собі
й відмітити свою; змінювати чужі й видаляти — лише власник і менеджер. Прострочені задачі й дати здачі — у «Студії», блок «Прострочки».

**Погодження етапів дизайн-проєкту.** Для типу «Дизайн-проєкт» під кожним етапом — кнопка **Погоджено клієнтом** (зберігається
одразу, з датою) і лічильник **Правки − / +** (зберігається кнопкою «Зберегти проєкт»). Клієнт у кабінеті бачить «✓ погоджено».
Позначка менеджера й зняття погодження записуються в «Історію етапу» (з 19.11.2026); якщо клієнт за цей час сам погодив етап чи
надіслав правки — див. розділ 17 («Проєкт змінився, поки ви редагували»).

**Клієнт погоджує сам (з 18.11.2026).** Коли етап дизайн-проєкту стоїть на **Приймання** (дизайнер натиснув «Етап виконано» → приймання,
або менеджер поставив статус) чи вже виконаний і ще не погоджений, клієнт у кабінеті (`/kabinet/proekty`, `/kabinet/obiekt`, 10 мов) бачить
«чекає вашого погодження» і кнопку **Погодити етап** (з підтвердженням). Після натискання — «✓ погоджено» з датою, власнику/менеджерам і
відповідальному — Telegram «✅ Клієнт погодив етап…», запис в Аудиті (`project.approve`). В адмінці позначка — «✓ Погоджено клієнтом … (у кабінеті)».
Етап на іншій стадії клієнт погодити не може; ремонт, будівництво й інші типи — без цієї кнопки (погоджують, як і раніше, актами).

**Проєктування: дизайн і архітектура (з 18.11.2026).** Вкладка «Проєктування» показує обидва типи. Для кожного етапу в картці проєкту:
- **відповідальний етапу** (список працівників) і **термін** (поле «Кінець»): працівник отримує Telegram «📐 Вам призначено етап», сам потрапляє
  в команду обʼєкта й бачить у `/kabinet/team` → «Сьогодні» **«Мій етап «…»»** (у роботі чи на прийманні — завжди; прострочений термін — червоним);
- **Правки − / + з N** — лічильник раундів правок і скільки їх входить у договір (порожньо — без обмеження); понад договір — позначка
  «понад договір» (додаткові правки — окремо, за домовленістю);
- **Результати етапу** — документи з цим етапом: у формі «Документи» оберіть тип **Візуалізації / Креслення / Специфікація** (або Акт) і етап.
  Клієнт бачить їх під етапом в «Онлайн-контролі»;
- **Історія етапу** — коли клієнт погодив чи попросив правки (з коментарем) і нагадування; клієнт історію не бачить.
У шапці картки — загальна готовність (% — середнє етапів), у списку — прогрес поточного етапу.

**Клієнт: «Погодити етап» або «Є правки».** Етап дизайну чи архітектури на **Прийманні** клієнт або погоджує, або натискає **Є правки** і пише,
що змінити. Тоді етап повертається **В роботу**, лічильник правок +1, власнику/менеджерам, відповідальному обʼєкта й відповідальному етапу — Telegram
«✏️ Клієнт просить правки…» з текстом, в Аудиті — `project.revise`. В адмінці під етапом — червоний блок «Правки від клієнта» й запис в історії.

**Зручність картки проєкту (18.11.2026).** **Зберегти проєкт** завжди внизу екрана; поки змін немає — контурна, зі змінами — заливка й
червоне «є незбережені зміни». «← До списку», закриття вкладки, **перемикання вкладок панелі** (з 19.11.2026 — CRM, Контакти, Студія…) й додавання
задачі/платежу/звіту/документа при незбережених змінах спершу питають (зберегти чи вийти). Те саме — у картці контакту, формі нового
проєкту, статті, товарі й редакторах сторінок. Прибрати вже збережений етап (✕) — з підтвердженням. У картці заявки CRM — швидкі дати
«Наступного контакту» (**Сьогодні / Завтра / +3 дні / +тиждень**), а закриття зі змінами (✕, «Закрити», Esc) — з підтвердженням.

**Безпека:** платежі, документи, задачі й видалення перевіряють, що обʼєкт видно цьому працівнику (інакше 404).

## 14. Заявка → пропозиція → проєкт (з 18.11.2026)

**Пропозиція.** У картці заявки CRM — блок **Пропозиція**: послуга (спершу пріоритетні: **Дизайн-проєкт інтерʼєру**, **Ремонт під ключ**,
**Будинок під ключ / коробка**, **Комерція: ремонт офісу**; далі планувальний і повний пакети дизайну, архпроєкт, меблювання, ландшафт), площа
(м², для ландшафту — сотки) і регіон **Україна / Європа**. Підсумок рахується одразу: «від $2 550 ($30/м² × 85 м²)»; дизайн — не менше
мінімуму ($2 500, Європа $4 000); де ставки немає (напр. офіс у Європі) — «за кошторисом». Ставки — лише з CLAUDE.md (той самий
`tools/site/rates.py`, що й калькулятор сайту). Тип і площа підставляються самі з тексту заявки (у заявок бота — з «Площа: …»).
**Зберегти розрахунок** — розрахунок записується в заявку й історію («Розрахунок: …»), нова заявка або «В роботі» переходить у **Розрахунок**
(і рахується взятою в роботу). Бачить і робить той, хто може змінювати заявку (власник, менеджер; дизайнер — свою).

**Створити проєкт** (одна кнопка, право «Створювати й редагувати обʼєкти» — власник і менеджер): з заявки переносяться клієнт, контакт,
тип і площа з пропозиції (без пропозиції — тип за текстом послуги), місто → адреса, відповідальний; етапи — за шаблоном типу; заявка переходить
у **Проєкт: етапи**, у картці проєкту — «З заявки CAS-… · джерело · сторінка-джерело». Повторно з тієї ж заявки проєкт не створюється
(відкривається існуючий). Клієнт: якщо заявку подано з кабінету — той самий акаунт; якщо номер уже підтверджено входом через Telegram-бота —
той акаунт; інакше створюється клієнт за номером: щойно людина увійде на сайт **за цим номером телефону**, вона побачить проєкт у кабінеті
(номер із профілю, який будь-хто може вписати, для цього не використовується). Якщо клієнт згодом увійде іншим способом (Google, віджет Telegram)
і не бачить проєкт — напишіть розробнику, щоб обʼєднати акаунти.

**Для розробника:** `migrations/0014_lead_offer.sql` (`orders.offer` JSON, `orders.project_id`); `PATCH /api/admin/crm {id, offer: {key, area, region}}`
(`OFFER`/`offerOf`/`offerLine` у `functions/api/admin/crm.js`, GET віддає `offers`); ставки — `functions/_rates.js`, ЗГЕНЕРОВАНО `python3 tools/site/rates.py`
(`--check` ловить розбіжність); конверсія — `POST /api/admin/projects {type: 'from_lead', order_id, title?}` (`leadClient`, `guessService`, `newProject`).
До міграції 0014 пропозиція відповідає 503 без часткових змін, конверсія працює. Тести — `tools/tests/crm2.mjs` (у складі `run.mjs`), Playwright — `ui.mjs` (owner-lead-offer).

## 15. Контакти: клієнти, підрядники, партнери, бригади, майстри (з 18.11.2026)

Вкладка **Контакти** (була «Партнери») — один довідник замість кількох списків (з 20.11.2026 — ще й режим **Таблиця** з сортуванням,
правкою клітинок, масовими діями, архівом та імпортом CSV — розділ 18). Типи: **Клієнт, Підрядник, Партнер, Постачальник, Ріелтор,
Бригада, Майстер**, а також Будівельна компанія, Дизайнер / архітектор, Інше. Швидкі фільтри одним дотиком (Усі / Клієнти / Підрядники /
Бригади / Майстри / Постачальники / Партнери), фільтри статусу, оцінки (від 3/4/5★) і регіону, пошук (імʼя, компанія, @username, телефон,
пошта, тег, нотатки), CSV.

**Картка контакту:** імʼя, компанія, тип, статус, регіон, телефон, Telegram, пошта, сайт, **оцінка 1–5★**, **спеціалізація-теги**
(плитка, електрика…), нотатки (бачать лише власник і менеджер); нижче — **обʼєкти** (клік відкриває обʼєкт, ✕ — відвʼязати) і **заявки**:
привʼязані явно та всі заявки з тим самим телефоном чи Telegram.

**Без дублів:** той самий телефон (у будь-якому форматі), Telegram, пошта, сайт або компанія — це один контакт (ручне додавання → «вже є»,
бот — лише доповнює запис). **Клієнт потрапляє в довідник сам**, коли менеджер натискає «Створити проєкт» у заявці: тип «Клієнт», привʼязка до
проєкту й заявки; друга заявка того ж клієнта — той самий контакт. Бот пошуку «Клієнтів» не створює (лише підрядників, бригади, постачальників…).

**Контакти обʼєкта:** у картці обʼєкта — блок «Контакти обʼєкта»: знайдіть контакт у довіднику, вкажіть роль («Плиточник», «Постачальник
вікон») і натисніть його — привʼязано. Команда обʼєкта (дизайнер, прораб, мебляр… — право «Контакти своїх обʼєктів») бачить ці контакти в
картці обʼєкта й у `/kabinet/team` (телефон — одним дотиком), але не бачить оцінку, статус і нотатки, не бачить довідник цілком і контакти чужих
обʼєктів. Бухгалтер контактів не бачить. **Клієнт контактів не бачить ніде.**

**Для розробника:** `migrations/0015_contacts.sql` — розширення таблиці `partners` (`email`, `rating`, `client_id`) і таблиця `contact_links`
(contact_id + project_id | order_id, role, note); до міграції довідник працює як раніше, пошта/оцінка → 503. API — `/api/admin/partners`
(`?find=`, `?id=` з `links`/`leads`, `POST {action: 'link'}`, `DELETE ?link=`), типи й `projectContacts`/`leadContact` — `functions/_partners.js`,
право `contacts.linked` — `functions/_roles.js` (дизайнер і польові ролі). Тести — `tools/tests/partners.mjs`; Playwright — `ui.mjs`
(owner-partners, owner-project-contacts, team-contacts).

## 16. КП, нагадування, відгуки, масові дії (з 18.11.2026)

CRM ведуть двоє — **власник і менеджер**: менеджер після входу одразу потрапляє в `/kabinet/admin` (кабінет працівника — за посиланням
«Мій кабінет працівника»), у CRM швидкий фільтр **Мої** стоїть одразу після «Усі». Функції дизайнера й прорабів лишаються.

**Надіслати КП.** Після «Зберегти розрахунок» у блоці «Пропозиція» зʼявляється готовий текст КП **мовою заявки** (10 мов сайту: послуга,
площа, «від $…», «точну вартість порахуємо після заміру й ТЗ», «консультація по телефону — безкоштовна»), його можна підправити.
Кнопки **Telegram / Viber / WhatsApp** відкривають чат клієнта (Viber і WhatsApp — уже з текстом; у Telegram текст скопійовано — вставте),
**Скопіювати** — у буфер. Сайт нічого не надсилає сам — пише менеджер зі свого месенджера; кожне натискання — рядок в історії заявки
«КП надіслано (WhatsApp): …» і запис в аудиті. Нова заявка або «В роботі» → «Розрахунок».

**«Є правки» від клієнта** — див. розділ 13 (кабінет клієнта, 10 мов; лічильник правок +1, Telegram відповідальним і власнику/менеджерам,
запис в «Історії етапу»).

**Нагадати клієнту про погодження.** Під етапом дизайну/архітектури на «Прийманні» — **Нагадати клієнту**. Якщо клієнт увійшов через Telegram
(віджет або номер через бота) — бот надсилає йому «етап … чекає вашого погодження» з посиланням на кабінет (мовою заявки). Якщо ні — зʼявляється
готовий текст і кнопки Telegram / Viber / WhatsApp, надсилання записується в журнал. Автоматично: етап на прийманні ≥ 24 год, клієнт у Telegram,
10:00–20:00 за Києвом — бот нагадає сам. **Без спаму:** не частіше 1 разу на 48 год на етап (і вручну, і автоматично), автоматично — не більше
3 разів на етап; кожне нагадування — в «Історії етапу» й Аудиті (`client.remind`). Пошти для розсилок у студії немає, тож лише Telegram або вручну.

**Попросити відгук у Google.** Через ~2 доби після статусу проєкту «Завершено» бот один раз надсилає клієнту (якщо він у Telegram) подяку й
посилання https://g.page/r/CbaVqfJBXWLQEAE/review (10 мов). У картці завершеного проєкту — **Попросити відгук у Google** (той самий текст;
без Telegram — кнопки месенджерів) і позначка «★ Відгук попросили … · канал». Удруге не просимо. Аудит — `client.review`.

**Масові дії.** У режимі «Таблиця» / «Список» біля кожної заявки — прапорець (і «вибрати всі»). **На канбані** (з 19.11.2026) —
кнопка **Вибрати кілька**: на картках зʼявляються прапорці (дотик до картки — вибрати, у заголовку колонки — «вся колонка»), картки в
цьому режимі не відкриваються й не перетягуються; **Готово** / «Вийти з вибору» — назад. Внизу — панель: **Змінити стадію…**,
**Відповідальний…**, **Не цікаво** (стадія «Скасовано», причина — в історії; заявки бота пошуку ще й навчають бота не показувати схожі),
**Скасувати вибір**. Кожна дія — з підтвердженням; сервер перевіряє права на кожен рядок (чужий або без права — пропускається, у підсумку видно,
скільки змінено). **Заявки бота пошуку** (джерело «Бот пошуку»): швидке посилання на Telegram автора, тип і площа підставляються в пропозицію,
«Взяти в роботу» і «Створити проєкт» — як для інших.

**Для розробника:** тексти клієнту 10 мовами — `functions/_client_msgs.js` (`kpText`, `remindText`, `reviewText`); нагадування й відгуки —
`functions/_nudges.js` (`remindStage`, `askReview`, `runNudges` — викликає `/api/admin/lead-sla` кожні 5 хв); `migrations/0016_client_nudges.sql`
(`projects.done_at`, `review_asked_at`, `review_channel`); поля етапу `review_at`, `remind_at`, `remind_n`. API: `PATCH /api/admin/crm
{id, offer_sent: telegram|viber|whatsapp|copy}`, `{bulk: {ids, status | assignee_staff_id | not_interested}}`; `POST /api/admin/projects
{type: 'remind', project_id, stage_id, channel?}` і `{type: 'review_request', project_id, channel?}` (право «Створювати й редагувати обʼєкти»).
Тести — `tools/tests/crm2.mjs`.

## 17. Одночасне редагування, довгі списки, ліміти (з 19.11.2026)

**«Проєкт змінився, поки ви редагували».** Картку проєкту можуть змінювати одночасно: менеджер у формі, клієнт у кабінеті («Погодити
етап», «Є правки»), другий менеджер, працівник («Етап виконано»). Раніше, якщо менеджер зберігав форму, відкриту до дії клієнта,
дата погодження чи правки зникали. Тепер кожна картка має **версію**: «Зберегти проєкт» надсилає версію, з якою форму відкрили, і якщо
проєкт відтоді змінився — сервер нічого не записує, а на екрані зʼявляється вікно з тим, хто й що змінив («Клієнт — клієнт погодив етап»):
- **Оновити й повторити мої зміни** — підтягуються свіжі дані, а ваші незбережені правки переносяться туди, де їх ніхто не чіпав.
  Якщо перетинів немає — усе зберігається одразу. Якщо те саме поле змінили і ви, і хтось інший — лишається свіже значення, а над формою
  зʼявляється список «зараз «…», ваше значення «…» не перенесено»: перевірте, виправте вручну й натисніть «Зберегти проєкт»;
- **Оновити без моїх змін** — показати свіжі дані, ваші правки відкинути;
- **Повернутись до форми** — нічого не робити (наприклад, щоб скопіювати набраний текст).

Те саме — у **картці заявки** («Заявку змінили, поки ви редагували») і **картці контакту**. Перетягування на канбані, «Взяти в роботу»
й масові дії працюють як раніше (вони змінюють одне поле).

**Погодження, правки, нагадування й історію етапу веде сервер.** Навіть якщо форма «Зберегти проєкт» про них нічого не знає (стара
вкладка, збій), дата погодження, «погодив сам клієнт», лічильник і текст правок клієнта, відлік нагадувань та історія лишаються.
Менеджер змінює погодження й лічильник лише своїми кнопками («Погоджено клієнтом», «Скасувати погодження», «Правки − / +») — і його
«+1» додається до того, що встиг надіслати клієнт, а не замінює.

**Довгі списки заявок.** CRM більше не обрізає список на 1000: показує перші 200 («Показано 200 з 3 412»), далі — кнопка
**Показати ще**; у «Таблиці» / «Списку» наступна порція підвантажується сама, коли догортали до кінця. Пошук, швидкі фільтри («Мої»,
«Нові», «Прострочені»…) і всі фільтри шукають **по всій базі**, а не лише по показаних рядках. На канбані, якщо завантажено не все, у
заголовку колонки — «200 з 310». «Нових без відповіді» рахується по всій базі. CSV — усе за фільтром (до 20 000 рядків).

**Ліміти записів працівників** — розділ 10 (з 20.11.2026 — ще задачі 600 / год, порції імпорту контактів 120 / год). Звичайна робота до них не доходить; якщо зʼявилось «Забагато змін поспіль — зачекайте
кілька хвилин», це або скрипт, що зациклився, або чужий доступ до акаунта — перевірте «Аудит» і натисніть «Вийти на всіх пристроях».

**Для розробника:** `functions/_ver.js` — версія = короткий хеш полів, які форма може перезаписати (міграція не потрібна):
`projectVer` (поля проєкту, етапи без службових `review_at` / `remind_*` / `hist`, команда), `leadVer`, `contactVer`; `conflict()` → 409
`{conflict: true, ver | row | partner, last: {by, what, at}}` (`last` — з `audit_log`, клієнт — без імені); `updateStages()` — запис етапів
«порівняй і заміни» (`UPDATE … WHERE stages IS <прочитане>`, до 4 спроб) для клієнта (`functions/api/account/projects.js`), кабінету
працівника (`team/action.js`) і нагадувань (`_nudges.js`). `PATCH /api/admin/projects`: зі `stages` версія обовʼязкова (428), запис —
теж «порівняй і заміни»; для збереженого етапу `approved_at` / `revisions` з форми ігноруються — лише `approve: true | 'РРРР-ММ-ДД' | false`
і `rev_delta: ±n` (`stagesOf`). `GET /api/admin/crm`: `limit` (1…1000), `before` (id), відповідь `total`, `more`, `next`, `waiting`,
`by_status`; рядки — з `ver`. Ліміти — `STAFF_LIMITS` / `staffLimited()` у `functions/_rate.js` (ключ — акаунт працівника).
Інтерфейс — `assets/admin/cms.v1.js`: `conflictDialog`, `merge3`, `clashBox`, сторож незбережених змін `GUARD` / `watchForm` / `canLeave`
(вкладки панелі, `beforeunload`), канбан — `PICK` / `setSel`, сторінки — `loadMore` / `moreRow`; помилка `api()` тепер має `status` і `data`
(`assets/account.v1.js`). Тести: `tools/tests/crm3.mjs` (у складі `run.mjs`: сценарій «клієнт погодив, поки менеджер редагував», гонки в ту
саму мить, ліміти, сторінки на 1 230 заявках), Playwright — `ui.mjs` (owner-project-conflict, owner-project-conflict-clash, owner-lead-conflict,
owner-crm-kanban-bulk, owner-tab-guard, owner-crm-pages, client-object), `xss.mjs` (owner-conflict-dialog, owner-conflict-merge).

### Задачі

Вкладка **Задачі** у `/kabinet/admin` (одразу після CRM; на вкладці — червоний лічильник прострочених):

- **Швидко додати:** напишіть назву в рядку вгорі й натисніть **Enter**. Строк (є кнопки «Сьогодні / Завтра / +тиждень»), виконавець, «Важлива»
  і привʼязка до заявки, обʼєкта (з етапом) чи контакту — за бажанням. Без виконавця задача ставиться собі. На телефоні додаткові поля
  сховані за кнопкою «Строк, виконавець».
- **Привʼязка в рядку задачі — кнопка:** назва обʼєкта відкриває картку обʼєкта, «Заявка №…» — картку заявки у вкладці «Заявки»
  (і тоді, коли заявку ховає поточний фільтр списку). Заявку в задачі бачить лише той, хто має право на заявки.
- **Перемикачі:** Мої / Усі / Прострочені / Сьогодні / Тиждень / Виконані — з кількістю. Фільтри: виконавець (і «без виконавця»),
  привʼязка, пошук. Список згруповано: Прострочені → Сьогодні → Завтра → Цього тижня → Пізніше → Без строку.
- **Виконано** — прапорець ліворуч (один дотик); 6 секунд унизу видно кнопку **Скасувати**. Виконані — у перемикачі «Виконані»,
  зняти прапорець — повернути в роботу.
- **Змінити** — натисніть на назву: задача розгортається у форму (назва, примітка, строк і час, виконавець, важливість, привʼязка).
  **Скасувати задачу** прибирає її з відкритих (лишається серед «Виконані» з позначкою «скасовано», звідти — «Повернути в роботу» або
  «Видалити назавжди»). Якщо задачу за цей час змінив інший — зʼявиться те саме вікно «… змінили, поки ви редагували», що й у картках.
- **Масово:** «Вибрати кілька» → позначте задачі → внизу: **Виконано**, **Перенести** (нова дата), **Виконавець…**. Кожна дія — з
  підтвердженням, до 100 задач за раз.
- **У картках:** блок **Задачі** є в картці заявки, обʼєкта й контакту — там задачі саме цієї заявки / обʼєкта / контакту й той самий
  рядок швидкого додавання (привʼязка ставиться сама). Додавання задачі не «бруднить» картку й не закриває її.

**Задачі етапів обʼєкта** (чекліст «Задачі по етапах» у картці обʼєкта, розділ 13) нікуди не переносились: вони лишаються у своїй таблиці
й у картці обʼєкта, а вкладка «Задачі» просто показує їх у спільному списку з позначкою «задача етапу». Звідси їх можна відмітити
виконаними, перенести дату й змінити виконавця; етап, назву й видалення — у картці обʼєкта. Так безпечніше: жодні наявні дані не чіпались.

**Хто що бачить.** Власник і менеджер створюють, призначають і бачать усі задачі. Решта (дизайнер, прораб, мебляр, геодезист, 3D-замір,
дрон, бухгалтер) бачать **лише задачі, призначені їм**, і можуть тільки відмітити «виконано» (з коментарем) чи повернути в роботу.
Привʼязку працівник бачить у межах своїх прав: назву обʼєкта — якщо він у його команді, заявку — якщо вона на ньому, контакт — якщо його
привʼязано до його обʼєкта (телефон — лише з правом на контакти клієнтів). Чужі назви, телефони й нотатки не показуються.

**Кабінет працівника `/kabinet/team`:** нова вкладка **Задачі** — мої задачі з великим прапорцем; дотик відкриває «Задачу виконано?» з
полем коментаря для автора. Виконані — нижче, у згорнутому списку (дотик по прапорцю повертає в роботу). Відкриті задачі видно й у
«Сьогодні» (прострочені — червоні).

**Сповіщення в Telegram** (бот сайту; працівник має один раз натиснути Start; без Telegram сповіщень просто немає):

| Подія | Кому | Коли |
|---|---|---|
| Задачу призначено (нова або перепризначена) | виконавцю, якщо це не він сам її поставив | одразу, якщо 10:00–20:00 за Києвом; інакше — зранку після 10:00 (кілька задач — одним повідомленням) |
| Задачу виконано | автору, якщо виконав не він сам | так само: одразу вдень або зранку |
| Зведення «Задачі на сьогодні» (сьогоднішні й прострочені, разом із задачами етапів) | кожному, в кого вони є | раз на день, перший прохід розкладу після 10:00; у суботу й неділю — лише якщо є задача зі строком саме сьогодні |

Нічого не надсилається поза 10:00–20:00 і не частіше одного зведення на день на людину. Розклад — той самий, що для заявок
(«⏰ Заявки — SLA 15 хв і звіт», кожні 5 хв), окремо нічого вмикати не треба.

### Таблиця контактів

У вкладці **Контакти** — перемикач **Список / Таблиця** (вибір запамʼятовується в браузері). У таблиці:

- **вкладки типів** з кількістю: Усі / Клієнти / Постачальники / Підрядники / Партнери / Бригади / Майстри / Ріелтори, окремо — **Архів**;
- **колонки:** назва / імʼя, компанія, спеціалізація (теги), місто, телефон, месенджер (Telegram), пошта, остання взаємодія (остання
  зміна, привʼязка чи задача), заявки / обʼєкти (кількість), відкриті задачі, оцінка, примітка. Кнопка **Колонки** — які показувати
  (запамʼятовується). Заголовок закріплений; на телефоні вбік гортається сама таблиця, а не сторінка;
- **сортування** — натисніть заголовок колонки (ще раз — у зворотному порядку); **пошук**, фільтри **Місто** й **Спеціалізація**;
- **правка на місці:** клацніть клітинку, виправте, **Enter** (Esc — скасувати). Телефон сам приводиться до +380…; якщо такий телефон,
  Telegram чи пошта вже є в іншого контакту — сервер не збереже й скаже про це. Якщо контакт за цей час змінив інший менеджер —
  зʼявиться вікно «Контакт змінили, поки ви редагували»;
- **швидке додавання:** перший рядок таблиці — заповніть і Enter (тип — з відкритої вкладки); «⋯» біля імені відкриває повну картку;
- **масові дії:** позначте рядки → **Тип…**, **Змінити місто**, **В архів** (усе з підтвердженням, до 100 за раз). Архів — замість
  видалення: контакт зникає зі списку й пошуку, але звʼязки з обʼєктами, заявками й задачами лишаються; повернути — вкладка «Архів»
  → позначити → «Повернути з архіву» (або кнопка в картці);
- **CSV** — вивантаження за поточним фільтром і сортуванням (до 20 000 рядків, UTF-8 з BOM — Excel відкриває кирилицю правильно);
- **Імпорт CSV:** оберіть файл (з Excel / Google Таблиць: «Зберегти як CSV», до 2 000 рядків) → зіставте колонки (назви вгадуються
  з першого рядка) і тип для рядків без типу → **Перевірити** — попередній перегляд: що буде додано, які рядки — дублі (той самий
  телефон у будь-якому форматі, Telegram, пошта, сайт чи компанія — у базі, в архіві або вище в цьому ж файлі) і де помилки (напр.
  некоректний номер) → **Імпортувати N**. Дублі й рядки з помилками пропускаються, нічого не перезаписується.

Таблицю, імпорт, масові дії й архів бачать лише **власник і менеджер** (право «Довідник „Контакти“»). Без права «Телефон, пошта й
адреса клієнта» телефони, Telegram і пошта не віддаються ні в таблиці, ні в картці, ні в CSV.

### Що зробити власнику після оновлення

## 19. Денний і нічний режим адмінки (з 23.11.2026)

- **Де перемикач:** кругла кнопка-іконка (сонце / місяць, 44 px) праворуч у рядку з роллю й іменем над вкладками
  /kabinet/admin («Денний режим», `aria-pressed`). Клік перемикає одразу, без перезавантаження.
- **Яка тема відкривається:** збережений вибір (localStorage `cas_adm_theme` = `light` | `dark`, у кожному браузері свій) →
  інакше тема системи (`prefers-color-scheme`, і змінюється разом із системою, доки нічого не вибрано) → інакше ніч.
  Тему ставить маленький інлайн-скрипт у `<head>` сторінки адмінки (`ADMIN_HEAD` у `tools/shop/pages.py`) ще до першого кадру — без мигання.
- **Що охоплено:** уся робоча область адмінки (CRM, канбан, таблиці, картки, діалоги, задачі, контакти, редактор, тости, масові дії).
  Шапка й футер сайту лишаються темними. Кабінет клієнта (/kabinet, /kabinet/obiekt…) не змінюється; кабінет працівника
  /kabinet/team має свою «польову» світлу тему (`assets/team.v1.css`) і перемикача не має.
- **Палітра:** день — тепла папірова (менеджер) і холодніша зі сталевим акцентом (власник, як графіт уночі); ніч — як і було.
  `color-scheme: light | dark` на `<html>` — рідні селекти, календар дати, прапорці й прокрутка в тон.
- **Як додати колір (розробнику):** лише через змінні. Палітра дня — `assets/admin/theme.v1.css` (`html[data-adm-theme=light] …`).
  Новий колір у `cms.v1.css` / `crm4.v1.css` / `studio.v1.css` чи в розмітці з JS — `var(--назва,<колір ночі>)`, а денне значення
  змінної — у theme.v1.css (як `--err`, `--err-hi`, `--on-err`, `--on-ac`, `--on-cmd`, `--hi`, `--shadow`). Жорстко зашитий колір у
  світлій темі зламається (біле на білому). Контраст — WCAG AA в обох темах (текст ≥ 4.5:1, межі полів і фокус ≥ 3:1).
- Тести: `ui.mjs` — `owner-theme` (система, клік, збереження, 44 px, шапка темна), `owner-theme-manager`, `owner-theme-scope …`
  (тема не потрапляє в кабінет клієнта й працівника): `ONLY=owner-theme node tools/tests/ui.mjs`.
